# 打印系统研发任务书

版本：V1.0 · 首期演示范围已确认，业务细则待逐项冻结。日期：2026-10-22（Asia/Shanghai）。

## 1. 目标和已确认范围

以云途智印当前商家后台为功能与外观参照，采用芋道后端＋Vue 3 管理端建立自有打印管理系统。第一期交付一个商家一个门店的服务端和后台，预留扩展；先可演示验收，小程序后续开发。用户明确要求页面外观也一致。打印客户端可复用条件未知，列为前置调研。

首期是可运行的业务系统演示版：使用真实数据库、服务端接口、权限与持久化，支持配置、查询和可重放业务流程。支付渠道、终端回执和未具备条件的外部通知采用显式模拟适配器，界面和验收报告标注模拟。首期交付不代表已经接通原客户端、实际收款或真实出纸。

覆盖基线为53个入口（52侧栏＋工作台）、23类二级表单和2个附属页。52入口可读，自动提现设置1入口权限受限。第一期不因小程序延期而删除后台已有小程序相关设置、订单分类、广告或会员功能。隐藏模块、平台总后台及未提供的其他角色不在已观察范围内；发现新需求进入变更清单。

本任务书确认的是研发范围、执行顺序与验收方法。文中未来任务的“验收”是要求，均不代表已经测试通过。当前交付只有文档与任务清单，没有实施软件、部署或实机验收。

## 3. 功能等价与外观一致的判定

功能等价要求在已确认规则下，相同输入、角色、配置与状态得到相同结果，并覆盖失败与边界场景。仅按钮存在、页面可打开、接口返回成功均不够。

外观要求覆盖顶栏/侧栏/页签、内容布局、字体字号、颜色、间距、表格、筛选区、弹窗、按钮、分页、交互反馈及默认状态。实施前补采截图基线；仅有广告截图和结构文本不足以证明全部页面像素一致。先固定视口、缩放、字体、数据状态和遮罩规则，再以截图对照与人工检查验收。视觉差异阈值须记录，不擅自改成“风格相似”。

没有原站样例的条件字段或动作结果，只能用明确的新设计供确认，不能标为已经复刻。自动提现当前只知道无权限态，必须保留功能缺口；演示入口可以存在，但“完整功能等价”验收需要补齐规则。后台演示验收、完整旧站等价验收、真实经营上线是不同检查点。

## 4. 架构与模块边界（建议设计）

先采用模块化单体服务，避免首期引入不必要的分布式运维。Java后端、Vue 3 管理端、关系数据库、Redis、文件存储及需要时独立运行的文件转换worker构成首期环境。实际框架版本、数据库/Redis/Node/包管理器版本必须通过BASE-01读取锁文件和实际构建后固定，不在本任务书里虚构已经兼容。

芋道提供可复用的身份、权限、文件、支付等基础能力；打印计价、文件处理、任务调度、终端协议和业务账务仍须按本项目规则实现。候选后端分支master-jdk17与JDK21仅作为版本核对起点；不能默认仓库master就是该技术组合。前端保留组件基础并重做原站外观外壳，不直接沿用默认芋道布局。

建议领域：组织权限、门店配置、商品价格、文件文库、报价订单、支付退款账务、打印任务与设备、预约配送、会员营销、广告通知、统计审计。首期每个业务实体携带门店归属，必要实体携带商家归属；服务端从认证上下文获得范围，不能相信客户端传入storeId。多商家开户、运营和计费平台不纳入首期。

管理端、未来小程序与终端分别使用各自身份和接口入口，共用报价/订单/账务/文件领域服务。模拟支付与终端接入同一业务接口，通过环境配置显式选择，保留可追踪的模拟标志；后续更换适配器不重写业务核心。

建议接口分区为管理API、用户API、终端API、外部回调API；具体路径由OpenAPI契约定稿。约定统一分页、排序白名单、金额精度、时区、业务错误码、幂等键、版本号和请求追踪ID。旧站参数数字与ASPX链接仅记录作菜单语义来源，不照搬成新系统状态编码。

建议实体：merchant、store、staff与role_scope；store_config与config_version；product、price_rule、binding_option；file_asset、conversion_job、library_item与category；quote_snapshot、print_order、order_item；payment、refund、wallet_ledger与settlement_request；print_task、task_attempt、terminal、printer、tray；delivery_task；member、level、recharge_rule、print_coupon；ad_slot、ad_asset；audit_event。最终表名、索引及事务边界在契约任务中给出。金额字段不用浮点数，历史订单保留商品及规则快照。

订单/账务落库与异步事件发出需有可恢复的一致性方案，例如Outbox记录、消费方Inbox去重与重试补偿；不把消息系统自身的投递保证当作业务恰好执行一次。终端配置区分期望、已接收、实际生效版本，重启生效项不能只以后台保存成功判定。

官方候选来源：[ruoyi-vue-pro](https://github.com/YunaiV/ruoyi-vue-pro)、[Vue 3管理端](https://github.com/yudaocode/yudao-ui-admin-vue3)、[后续uni-app参考](https://github.com/yudaocode/yudao-mall-uniapp)。技术审查已于2026-10-22核对README；尚未克隆、编译和验证本项目版本组合。

## 5. 核心业务不变量与待冻结规则

### 5.1 报价与资金

服务端统一报价；明确“页、面、张、份”及单双面单价单位，区分计费纸张与实际输出纸张。阶梯按单文件还是合并计算、阈值大于还是大于等于、特殊类型/打印机附加费/装订/配送/会员优惠/免费额度/最低消费的先后顺序必须用算例冻结。旧页面的奇数双面公式只是观察提示，不能跳过单位确认。

单价和中间计算采用约定定点精度，最终收款金额采用最小货币单位或精确定点；注明每一步何时舍入。订单创建保存报价版本与分项明细，价格变更不得改变已支付订单。收款、退款和钱包流水具有唯一业务键，重复请求/回调不重复记账。余额、赠送额、实际支付和可退额需要分别定义。

观察到打印券激活后进入用户余额；不得未经确认把打印券做成普通订单折扣券。提现/分账页面的跳转地址也不能用来断定支付服务商。模拟渠道保留真实领域约束，但不伪造第三方成功凭据。

### 5.2 状态与打印

文件处理、付款、退款、打印和配送采用独立状态。以下是新系统建议状态，需DISC-03确认编码和动作，不声称等同原站内部实现。

| 领域 | 建议状态链 | 关键异常与约束 |
| --- | --- | --- |
| 文件 | 已接收→处理中→可用；失败/已过期 | 不可用文件不能进入可执行打印任务 |
| 支付 | 待支付→成功；关闭/失败/结果待查 | 超时后迟到成功要查询补偿；不能凭前端结果记账 |
| 打印 | 待派发→已领取→已受理→执行中→成功 | 失败、部分成功、取消、结果不明单列；回执层级不足则不能称物理完成 |
| 退款 | 申请→审核/处理中→成功；拒绝/失败/结果待查 | 可退金额上限与并发控制；退款完成不改写打印历史 |
| 配送 | 待备货→可取件/待配送→已完成 | 配送取消和打印取消不能自动互相替代 |

订单聚合状态由上述状态按规则投影，所有操作检查权限、前置状态和版本。手工标已打印须记录操作者及原因，并与设备回执完成区别。打印任务包含稳定jobId、文件摘要、参数快照、目标设备、尝试记录和回执序号；结果不明时先核实，不能自动无限重试。补打是否收费、部分成功是否退费需业务确认。

### 5.3 权限、数据与文件

普通员工、财务、运营、维护是已观察角色名，详细权限矩阵尚未验证。新增后台管理员作为项目角色设计需记录。菜单、按钮和数据权限必须在服务端落地；下载文件、退款、提现、修改余额和手工打印分别鉴权。文件使用受控访问及期限，转换运行环境设置资源限制，日志不保存凭据和文件正文。

登录页不在已登录账号的53入口观察范围中，但新系统需要登录、退出、会话过期及账号恢复流程，因此另列AUTH-01。其原站外观和行为需补采，不以默认框架页面冒充已观察结果。

首期使用合成测试数据。用户文件保留期限、删除语义、备份保留期与账户注销影响仍待确认。保留可复现演示数据脚本与恢复点，禁止依赖原站用户真实文件作测试。

决策字段是有作用范围的限制，不是全局硬阻断：D05未知客户端不阻断模拟器；D07未知服务器不阻断本地部署；D13真实渠道未准备不阻断模拟资金流程；D14未定历史迁移不阻断合成数据备份恢复。JSON中的decision_gate_policy逐项记录该语义。未知业务规则仍须确认后才能通过对应等价性验收。

REL-01首期交付与REL-03恢复演练均应完成；REL-02是否完成取决于服务器资源。受限功能未补齐时，可以交付有明确限制的演示版，但不能宣布完整复刻验收通过。所有后续任务保留，不用延期等于删除范围。

## 8. AI执行、审查与任务交接规范

主对话作为负责人管理任务依赖、决策、版本和发布门禁。业务规则/复杂架构/独立复核建议GPT-6 Astra High；工程实现、联调、测试和部署建议GPT-6.1 Sol High，简单文案整理可用较低推理强度。模型选择是分工建议，不能替代验收结果；可按实际可用模型调整。

默认最多同时推进三个有独立文件责任的子任务，主对话负责集成。各模块明确代码归属，接口与数据库迁移由负责人协调。适合短审查的工作用子agent；需要长期跟踪的服务端、前端、测试部署再建立子对话，并引用同一版本任务书。未冻结契约前不让不同对话各自发明订单或金额模型。

每次派单提供：任务ID、目的、前置证据、输入文件、允许修改目录、禁止触碰范围、契约版本、必须完成项、验收命令、交付文件及阻断条件。子agent完成后报告：变更文件/提交号、测试命令与结果、证据路径、未完成项和风险。主对话复核后才能把任务状态改成完成。

任务状态统一为待执行、进行中、待决策、待资源、待验收、完成。缺少规则时先做不依赖规则的部分；对受影响功能留下待决策，不能把自己的猜测写成用户要求。完成标准是实际产物与证据，不是token用量、运行时长、页面数量或agent自述。每日进展用已完成/验证证据/阻断/下一步四项说明。

## 9. 部署、交付与后续上线

首期须提供可重复构建、配置示例、数据库迁移、合成数据、启动/停止/健康检查、文件存储路径、日志定位、备份恢复及回滚步骤。数据库与文件备份要配套并在隔离环境恢复核对。配置区分本地/测试/生产，密码及密钥通过环境或受控配置注入。

性能指标须根据实际设备与文件样本测量并记录，未确认并发和文件上限时不承诺生产容量。演示脚本至少展示配置保存、角色限制、上传报价、订单与模拟支付/打印、异常恢复、会员账务与图表数据对应。

真实上线前需另完成第三方资源、真实收款退款对账、打印机逐型号验证、现场异常处理、备份恢复演练和回退窗口。若首个经营入口是小程序，还要完成小程序真机验证与平台发布；若是现有电脑客户端，则验收该客户端入口。当前小程序入口仅是调研线索，不能证明已取得源码或对接协议。
